# GraalVM 25.5 (P)

The engine, its bundled JDK and every GraalVM Maven package are held at GraalVM
CE 25.0.1 (Note [GraalVM Is Held At 25.0.1] in `project/Dependencies.scala`,
#36). This design moves them to the GraalVM CE **innovation line, 25.5.x**, and
then re-runs the JVM-by-default gate on the upgraded build. It is "P" of
discussion #518. The JVM-by-default spec (`2026-11-03-jvm-by-default-design.md`,
"Stage 1, alongside: the GraalVM upgrade") fixes its place: **stage 3 must not
ship before it**, and the gate must be confirmed on the GraalVM that ships.

Numbers marked _measured_ come from the open-time harness (`perf:open`, release
build, ms from the click, medians of cold first opens) on the owner's Windows
machine (32 logical CPUs; 4 and 8 emulated with `start /affinity`). Research
notes: P (the #36 analysis and the 25.1–25.5 changelogs), N1 (the 25.5 swap,
Phase 4), M3 (JVM vs native after #647–#651) and the warm engine's measurement
(#659).

## Decisions already made (owner, 2026-11-08)

- **Target: GraalVM CE 25.5.x**, the newest 25.5 build when the bump PR is cut.
  25.0.2 is the last Community build on the 25.0 LTS line; only the innovation
  line gets security fixes in Community.
- **`-Djdk.graal.UsePriorityInlining=false`** goes in `jvm.options`. 25.3 made
  priority inlining the default; on 25.5 it doubled JIT CPU and cost about 0.2 s
  per open (measured, below).
- **First step: the #36 workaround.**
  `-da:com.oracle.truffle.host.HostExecuteNode` wherever tests run with `-ea`.
  Upstream is oracle/graal#14943. Without `-ea` GraalVM picks the right overload
  through the uncached path (verified on Windows and Linux).
- **Then the stage 3 re-gate on the upgraded build:** 8 logical CPUs, JVM within
  1.5× native, welcome and `image` templates, with the warm spare engine
  (#657/#658/#659), using `perf:open`'s `jvm-spare` engine and #659's pooled
  method.
- **Native image is removed next** (separate spec). P keeps the existing native
  build green until then and invests nothing in native-only fixes beyond that.

Platforms are unchanged: Linux x64 and aarch64, macOS aarch64, Windows x64 (no
macOS x64, as today).

Three things about the innovation line break assumptions the build makes:

1. **The JDK and the Maven packages no longer share a version.** On 25.0.x both
   were `25.0.1`. Now the JDK says `25.0.5.0.3` and the jars say `25.5.5.0.3`.
   `GraalVM.versionCheck` requires them equal, and `toolchain-pins.mjs` reads
   one `graalvm` pin into both.
2. **Versions have five components.** `GraalVM.toSemVer` throws on anything but
   one to three, and `GraalVMVersion.isCorrectVersionFormat` (the engine
   manifest's `graal-vm-version`) accepts at most four.
3. **Release tags and asset names changed.** The JDK is under `graal-<release>`
   with `graalvm-community-jdk-25i5-<jdk>_<os>-<arch>_bin`, not `jdk-<jdk>` with
   `graalvm-community-jdk-<jdk>_…`. GraalPy's standalone is
   `graalpy3.13-community-<v>`, not `graalpy-community-<v>`, and its version
   (25.5.5) is neither of the other two.

## Design

### 1. The #36 workaround (PR 1, on 25.0.1)

**The defect.** Since 25.0.2, `HostExecuteNode.createPrimitiveTargetCheck`
builds the type check for argument _i_ from overloads already inapplicable at
another argument _j_. With `-ea`, `fillArgTypesArray` asserts that the cached
types still validate (`HostExecuteNode.java:451` on 25.5) and fails, for example
for `new BigDecimal(BigInteger, int)` called with two `long`s. Without `-ea` the
cached guard fails, the call falls back to the uncached path and that picks the
right overload. The only cost is lost overload caching at those call sites. It
is unfixed in 25.0.5.0.3 and 25.5.5.0.3 (reproducer: `P/repro/Repro2.java`).

**The workaround** disables assertions for that one class wherever assertions
are on. Java applies a class's assertion status to its nested classes, and
class-specific settings win over `-ea` whatever their order. Truffle's own
assertions stay on elsewhere.

| Where                                                           | Today                                                                                                                         | Change                                                                                                                                                              |
| --------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Standard Library tests, JVM and native                          | `tools/build-scripts/src/stdlib-test/invocation.ts`: `JAVA_TOOL_OPTIONS: -enableassertions …`                                 | append `-da:com.oracle.truffle.host.HostExecuteNode`; it reaches `enso --jvm`, the native runner's guest JVM and any JVM a test spawns; update `invocation.test.ts` |
| sbt engine tests and runs                                       | `build.sbt`: `truffleRunOptionsSettings` (`"-ea" +: …`), `std-tests` (`Test / javaOptions`), `ydoc-server` `Compile / run`    | one `val testAssertions = Seq("-ea", "-da:com.oracle.truffle.host.HostExecuteNode")` used by all three                                                              |
| The launcher's JVM under assertions                             | `engine/runner/…/Main.java` `launchJvm`: adds `-ea` when its own assertions are on (test builds, `ENSO_LAUNCHER=native,test`) | add the `-da` after it                                                                                                                                              |
| Native test builds                                              | `build.sbt` launcher options: `-ea` when `GraalVM.EnsoLauncher.test`                                                          | add the same `-da` (Native Image takes `-ea`/`-da` at build time)                                                                                                   |
| Engine runs from sbt (indexing, `EnsoLint`, `runEnginePackage`) | `project/DistributionPackage.scala` `appendJvmOpts = "-ea"`                                                                   | `-ea -da:com.oracle.truffle.host.HostExecuteNode`                                                                                                                   |
| By hand                                                         | root `CLAUDE.md`, "Running an Enso test project by hand": `JAVA_TOOL_OPTIONS="-enableassertions"`                             | add the `-da`                                                                                                                                                       |

`jvm-interop`'s tests already enable assertions only for `org.enso.jvm...` and
need nothing. One Note, [HostExecuteNode Assertions Are Off Under Test] in
`build.sbt`, explains it; every other site refers to it. The Note names
oracle/graal#14943 and says to drop the flag when a release fixes it.

**Tests.**

- A runtime-integration test calls, from Enso, the two overload sets of the
  reproducer: a test class with `(BigInteger, int)` and `(int, StringBuilder)`
  constructors, and `BigDecimal.new` with two integers. It asserts which
  overload ran, three times each so the cached path is exercised. It runs under
  the sbt test options above, so it checks both that the `-da` is in effect and
  that the uncached fallback picks correctly.
- The same test asserts
  `Class.forName("com.oracle.truffle.host.HostExecuteNode").desiredAssertionStatus()`
  is false while `Main.class.desiredAssertionStatus()` is true, so a later edit
  that drops the `-da` fails here, not 20 minutes into the Standard Library
  jobs.

PR 1 lands on 25.0.1, where the assertion never fires, so it changes nothing and
can be checked on its own. PR 3 then needs no test-option changes.

### 2. Two GraalVM versions (PR 2, on 25.0.1)

The build learns that the JDK and the jars have different versions, still on
25.0.1, where the two values happen to be equal. This keeps PR 3 to the bump
itself.

**`project/Dependencies.scala`.**

- `graalVersion` is the **JDK** version, as `java.vm.version` prints it before
  the `+` (`25.0.5.0.3` after PR 3).
- `graalMavenPackagesVersion` is the **release**, the Maven version
  (`25.5.5.0.3`). Both names stay (the toolchain script and the pin policy match
  them by regex).
- New `graalPyVersion`, the standalone GraalPy release (`25.5.5`), for
  `test/Examples_Tests` only.
- Note [GraalVM Is Held At 25.0.1] becomes Note [GraalVM Follows The Innovation
  Line]: which value is which, why they differ, and the #36 flag.

**`project/GraalVM.scala`.**

- `versionCheck` stops requiring the two equal. It requires that
  `java.vm.version`'s prefix equals `graalVersion` (exact string, no SemVer
  parsing), and that its `jvmci-<major>.<minor>` part equals the first two
  components of `graalMavenPackagesVersion`. That is the real constraint: since
  25.1 Truffle's optimising runtime runs only on a GraalVM JDK of the same
  feature release (GR-73953). On 25.0.1 the JDK prints `jvmci-b01`; there the
  check falls back to the major version.
- `toSemVer` and `isSameVersion` go; nothing else uses them.
- `downloadLink` points at `releases/tag/graal-<graalMavenPackagesVersion>`.

**`build-config.yaml` `toolchain:`** gets one pin per version, each a bare value
as `setup-jvm`'s awk needs:

```yaml
toolchain:
  graalvm: 25.0.1 # the release: Maven packages and the download tag
  graalvm-jdk: 25.0.1 # what `java -version` prints
  sbt: 1.10.6
  flatc: 24.3.25
  graalpy: 25.0.1
```

**`tools/ci/toolchain-pins.mjs`** (and `check-workflows.mjs`): `graalvm` ↔
`graalMavenPackagesVersion`, `graalvm-jdk` ↔ `graalVersion`, `graalpy` ↔
`graalPyVersion`. `checkNativeLibsFixtures` keys on `graalMavenPackagesVersion`:
the fixtures name jars (`component/truffle-api-<v>.jar`), and jars carry the
Maven version. Tests in `check-workflows.test.mjs` and `toolchain-pins.test.mjs`
move with it.

**`.github/actions/setup-jvm`.**

- GraalVM: `graalvm/setup-graalvm@v1` documents innovation releases only for
  Oracle GraalVM (`version: '25.4'`, `distribution: 'graalvm'`). PR 2 tries
  `distribution: graalvm-community` with the release version on a throwaway
  branch on 25.5. If it does not resolve, setup-jvm downloads the CE archive
  itself, as it does flatc and GraalPy:
  `graalvm-ce-builds/releases/download/graal-<graalvm>/graalvm-community-jdk-25i<minor>-<graalvm-jdk>_<os>-<arch>_bin.<ext>`,
  checks the published `.sha256`, unpacks it and sets `JAVA_HOME` and `PATH`.
  The 25.0.x URL scheme stays as the branch for a release whose `graalvm` and
  `graalvm-jdk` are equal, so PR 2 is a no-op on 25.0.1.
- The toolchain check greps `$GRAALVM_VENDOR $GRAALVM_JDK` in `java -version`.
- GraalPy: the asset name is read from the release. `graalpy3.*-community-<v>`
  first, then `graalpy-community-<v>`.

**`tools/build-scripts` `toolchain-check`** (`src/toolchain/check.ts`): GraalVM
expects `graalvm-jdk`; the GraalPy parser accepts the 25.5 `--version` text
(checked against the real binary in PR 3). Its hint names the right download
tag.

**The engine manifest and the runtime downloader**
(`lib/scala/runtime-version-manager`). `DistributionPackage` writes
`graal-vm-version: <graalMavenPackagesVersion>` and
`graal-java-version: <graalVersion>` into `manifest.yaml`.

- `GraalVMVersion.isCorrectVersionFormat` accepts up to five numeric components.
- `GraalCEReleaseProvider` knows the innovation tag and asset scheme, derived
  from the two values.
- Its tests get a 25.5-shaped manifest.

The IDE never downloads a runtime (it bundles one). The manifest is still parsed
by anything that reads an engine's `manifest.yaml`, so a five-part version must
parse.

**`jvm.options`** (`distribution/engine/jvm.options`) gains, with its comment:

```
# Graal's pre-25.3 inliner: 25.3+ priority inlining doubled JIT CPU while a project
# opens (#518, P). Applies to Truffle's compilations through libgraal.
-Djdk.graal.UsePriorityInlining=false
```

Since #649 the host JIT is C2 (`-XX:-UseJVMCICompiler`), so the flag now affects
only Truffle's guest compilations. N1's measurement was taken before #649, with
Graal as the host JIT. PR 3 reports the open time with and without the flag on
the current develop (8 CPUs, welcome, `jvm-spare`, two rounds) as a record of
what it does now. The flag ships either way (owner's decision).

**The AOT cache retrains by itself.** The shim's key
(`app/project-manager-shim/src/jvmAot/key.ts`) hashes the app version, the
engine's path, the runtime's path (whose directory name now carries the new
versions) and `jvm.options`' text. PR 3 changes the second-to-last and the last,
so every user trains a new cache on first launch and the old key's directory is
deleted. No code changes. PR 3 checks:

- that training succeeds on 25.5 (`JDK AOT cache: trained in …` in the Electron
  log, and an empty `use.log` after an open);
- the cache's size against 25.0.1 (N1 measured 152.8 MiB against 169.6 MiB).

The warm spare (#658) uses the same cache and needs nothing.

**Peak guard.** The stage 1c guard was "no `Table|Vector` benchmark more than 5%
worse". M1 showed it cannot pass even on noise: two baseline runs of the same
build differ by more than 5% on 13 short benchmarks. A JDK change also cannot
run both arms in one job, because `std-libs-benchmark.yml`'s `jvm-options`
compares options on one JDK.

So:

- Dispatch `std-libs-benchmark.yml` with `bench-name=Table|Vector` three times
  on develop, with `jvm-options=-XX:-UseJVMCICompiler` (the product's flags on
  25.0.1).
- Dispatch it three times on the PR 3 branch, with
  `jvm-options=-XX:-UseJVMCICompiler -Djdk.graal.UsePriorityInlining=false` (the
  product's flags on 25.5).
- Alternate the dispatches in time.
- Compare the candidate arms: for each of the 97 benchmarks, the median of three
  against the median of three.

**Pass:**

- the median change over all benchmarks is at most +2%;
- no benchmark is more than 5% worse in all three develop/branch pairs.

A benchmark that fails the second rule is traced with Truffle's compilation
trace before merging, and reported. The default arms of the same jobs (no flags)
are reported, not gated. `engine-benchmark.yml` (runtime benchmarks) runs once
each side and is reported only.

### 5. The re-gate (after PR 3 and #659 merge)

The procedure is #659's ("At 4 or 8 CPUs" in `app/electron-client/CLAUDE.md`),
on a release IDE built from develop with `ide-local` in a worktree:

- **Machine:** the owner's Windows machine, idle.
- **CPUs:** the whole run pinned with `start /affinity FF` (8 logical CPUs).
  Every report's last line must confirm 8, or the block is discarded and rerun
  once.
- **Quiet check** before every block: 60 consecutive 1 s samples under 12% total
  CPU.
- **Command:**
  `perf:open --engines native,jvm,jvm-spare --template welcome,image --runs 2`
  per block, three rounds, with the engine order rotated between rounds.
- **AOT cache:** the shim's own, prepared before the measured launches, as the
  harness does for `jvm`. Its training time and size are recorded.
- **Credentials** unset, as in every run.
- **Pooled** with `perf/poolReportsCli.ts` into one report per template.

**Pass criterion.** The pooled first-open ratio `jvm-spare`/`native`:

| Both ratios (`welcomeShown`, welcome; `libraryShown`, `image`) | Outcome                                  |
| -------------------------------------------------------------- | ---------------------------------------- |
| ≤ 1.5                                                          | pass: the stage 3 switch PR may go ahead |
| 1.5 to 1.6                                                     | the owner decides from the report        |
| > 1.6                                                          | fail                                     |

Every `jvm-spare` first open must complete and must have used a spare. A hang,
or an open that took no spare, is a failed run, never dropped (Note [The Gate
Drops Nothing]).

## Rollback

- **PR 3 is one squash commit.** Reverting it restores 25.0.1 in one step:
  Workflow Lint holds all pins together, so a partial revert cannot pass.
  - PRs 1 and 2 stay; they are correct on either version.
  - Users' AOT caches retrain once more, because the key changes back.
  - IR caches and bindings are keyed on the engine version, not GraalVM's, so
    nothing else is invalidated.
- **A defect found after merge** in one area (a host-interop change, Python
  3.13) is fixed forward if small. Otherwise PR 3 is reverted, and the defect is
  filed with a reproducer as a draft issue on the fork. No upstream posts
  without the owner.
- Stage 3 has not shipped at this point, so no user's default changes with any
  of this.

## Risks

- **`setup-graalvm` and innovation CE.** If the action cannot install CE 25.5,
  setup-jvm downloads the archive itself (PR 2). That is one more download path
  to own, with the checksum checked.
- **Host-interop behaviour.** #36 shows host interop is where a GraalVM bump
  hurts Enso, and a JVM default routes every library's Java through it. The
  `OffsetDateTime` interop (25.4) and `Message` resolution by name (25.1) are
  the known changes. The Standard Library suites on both runners are the check.
- **Peak.** The new inliner (with the flag off), loop optimisations, and the
  call-site-frequency inlining for guests can each move peak either way. The
  noise-aware guard catches consistent regressions only.
- **The 4-CPU hang.** N1 saw 1 hung JVM launch in 5 at 4 CPUs on 25.5, the same
  signature as on 25.0.1 (first execution never scheduled). The re-gate counts
  hangs as failures. A hang at 8 CPUs is traced before any switch.
- **The innovation line moves monthly.** Each release is superseded by the next,
  and only the newest gets fixes. The two-pin layout and the checklist above
  make a later bump one PR. How often is an open question.
- **Native image.** A 25.5 builder change could need more than small fixes, just
  before native is removed (open question 3).
- **Python 3.13.** Polyglot Python code written for 3.12 may behave differently.
  Only `Examples_Tests` exercises it in CI.
